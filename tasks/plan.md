# Implementation Plan: Phase A — ④ ART Master Agent (2026-09-01 ~ 10-01)

## Overview

WBS(`docs/ART_agentic_wbs.md` §5, A-01~A-26)의 엔지니어링 실행판. ④ ART Master Agent — 처리 경로 분기 → 근거 검색(RawPedia·Issues) → 인용 답변, 실행 요청 → .arp 생성 → ART-cli 렌더링 폐쇄 루프를 **10/1 중간발표에서 시나리오 4단계 데모**로 완성한다. Phase B(①)는 중간발표 이후 rolling-wave로 별도 계획한다(FiveK 승인·태깅 게이트 결과가 선행해야 관찰 오류가 없음).

**Task list target: `tasks/todo.md`** — 프로젝트에 지정된 외부 트래커 없음(AGENTS.md 무관련). 각 태스크 카드에 WBS 코드(A-XX)를 병기해 역추적 가능.

## Architecture Decisions

- **패키지 레이아웃**: `src/artagent/` + `tests/` 신규. 데이터 수집·청킹 프로그램의 위치와 파일명은 각 태스크 구현 시 결정한다. 루트 venv(Python 3.14) 재사용.
- **의존 관리**: 증분식 — 소비 태스크가 필요할 때 pip 설치 + 설치 기록 문서에 append. 목록 파일화(pyproject 등)는 의존성이 실제로 쌓인 뒤(T8~T13 경) 기록을 옮기는 형태로 그때 결정한다. 미리 만들지 않는다.
- **Vertical slicing**: 9/1~9/11은 수집·질문셋·검색 기반을 만드는 확정 구간이다. 그 뒤 직선 답변 경로 → 라우터·강화 검색 → 프로필 루프 → 평가·데모 순으로 연결한다.
- **검색·청킹**: 검색 저장소는 Chroma로 고정한다. T4의 RawPedia 원문과 T10-2a의 정제 GitHub 후보를 T8-1 질문셋으로 연결한다. T8-2는 두 출처를 각각의 구조에 맞게 청킹하고, 같은 임시 Chroma에서 청킹·임베딩 조합을 비교한다. 청킹 규칙·글자 수·오버랩·직렬화 형식·임베딩 후보는 미리 정하지 않는다. 청크에는 본문, 구분 가능한 식별자, 원문 또는 후보 항목 식별자, 원문 위치가 있어야 한다. 비교는 출처별 Hit@k·MRR@k와 두 출처 평균, 실행 부담을 기록해 한 조합을 고른다. T9는 9/9~10에 공통 적재·검색 경로를 만들고, 9/11 T8-2의 선정 결과를 적용해 실제 저장소를 구성한다. 답변 생성은 T11에서 하고, 리랭킹과 k 튜닝은 T15에서 다룬다.
- **9/1~9/11 흐름**: 김구는 프로젝트 베이스를 만든 뒤 수집 문서 질문셋과 벡터DB 공통 경로를 담당한다. 김대성은 RawPedia 원문 수집 뒤 두 출처 문서의 청킹·임베딩 모델 시험을 담당한다. 고태우는 GitHub 원문 수집·정제 뒤 LangGraph 상태·노드·전이 설계를 담당한다. 9/11에는 T8-2 선정 결과를 T9 실제 저장소에 적용한다.
- **검색 평가 근거**: 검색 단계와 답변 생성 단계는 분리해 평가한다. 검색 결과와 기준 문서 ID를 비교하는 방식은 [LlamaIndex Retrieval Evaluation](https://llamaindex.openml.io/python/framework/understanding/evaluating/evaluating/) 및 [RAGAS ID-based Context Recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/)에, 두 단계를 나눠 평가하는 방식은 [LangSmith intermediate-step evaluation](https://docs.langchain.com/langsmith/evaluate-on-intermediate-steps)에 근거한다.
- **처리 경로 분기**: T13-1은 9/8~9/11에 주제 라벨이 아니라 다음 처리 경로를 고르는 상태·노드·전이 규칙과 20개 경로 라벨을 설계한다. 문서 질문은 RawPedia 검색, 문제 해결은 Issues·Discussions 검색, 실행 요청은 프로필 생성·ART-cli 렌더링으로 보낸다. T13-2는 그 설계를 구현한다.
- **W3 병렬 착수**: T14의 재작성·HyDE 구현·평가는 T8-1 질문셋과 T9 검색 모듈로 시작한다. T13-2가 T13-1 설계를 받아 라우터를 구현한다. T14·T17의 그래프 연결은 T13-2 뒤에 수행한다. T15는 T14 뒤에 수행한다. T16은 T17의 `근거 부족` 상태에서만 T14를 한 번 거쳐 재검색하고, T13-2 뒤 그래프에 연결한다.
- **.arp 생성**: 자유 텍스트 생성 금지. T19에서 실행 요청에 필요한 키를 선택하고 제약을 정의한 뒤 구조화 생성한다. T2의 PPVERSION 기록과 **ART-cli 실행 자체**를 검증 기준으로 사용한다.
- **코퍼스 정책**: GitHub Issues·Discussions는 공개 API·검색 전용(재배포 아님)으로 주 1회 증분 동기화한다. T10-1이 원문 변경분을 보관하고, T10-2a가 실제 플랫폼 신호에 따른 검색 후보 정제 규칙을 만든다. T8-2가 정제된 GitHub 후보를 해당 글 구조에 맞게 청킹해 공통 실험에 제공한다. T10-2c는 선정 뒤 같은 규칙으로 변경분만 T9 저장소에 반영한다. 원문 동기화 상태와 벡터 반영 상태는 별도로 기록한다.
